# nasrelay

NAS에서 실행하는 양방향 FTP·SFTP·WebDAV 파일 전송 Docker 애플리케이션입니다. 스마트폰의 웹 UI에서 작업을 등록하면 NAS가 전송하며 **브라우저를 닫아도 작업은 계속됩니다.** 텔레그램으로 결과 알림과 `/status` 조회를 지원합니다.

- 버전: **1.2.2**
- 이미지: `ghcr.io/maratangnearl/nasrelay:latest`
- 고정 버전: `ghcr.io/maratangnearl/nasrelay:1.2.2`
- 플랫폼: `linux/amd64`, `linux/arm64`

## 주요 기능

- FTP·SFTP·WebDAV 서버 ↔ NAS, 파일 및 폴더 재귀 전송, 빈 폴더 포함
- 원격 서버와 NAS를 나란히 탐색, 경로 직접 입력, 상위 폴더, 검색, 새 폴더 생성
- 각 탐색기의 **표시 필터**에서 수정 날짜·만든 날짜 표시 선택, **정렬**에서 제목·수정 날짜·만든 날짜·크기 기준과 오름차순/내림차순 선택
- 마우스 드래그 영역 선택, Ctrl/⌘ 다중 선택, Shift 연속 선택, 전체 선택
- 스마트폰에서는 체크박스로 다중 선택, 폴더 이름을 눌러 탐색
- 파일 행 우측 핸들을 반대쪽 패널에 드래그해 전송 등록
- 서버 프로필 여러 개 저장·선택·수정·삭제, 프로필별 연결·연결 해제 및 상태 표시
- 여러 서버 동시 연결 및 최대 4개 서버 작업 동시 전송, 작업 이력과 텔레그램에 서버 이름 표시
- FTP 및 명시적 FTPS, 패시브 모드, UTF-8/CP949/EUC-KR
- SFTP 비밀번호 인증 및 SHA256 SSH 호스트 키 검증
- WebDAV HTTP/HTTPS, Basic 인증, 파일·폴더 탐색과 양방향 전송, 다운로드 시 CDN 리디렉션 지원
- 복사 / 이동 선택, 전송 확인, 진행률·실시간 전송속도·대기열·일시정지·재개·취소·재시도·완료 기록
- 텔레그램 성공·실패·취소 알림: 완료 파일 수 및 총 파일 수, 완료 용량 및 전체 용량
- 텔레그램 `/status`: 전송률·현재 전송속도·파일 수·용량·현재 파일, 작업이 없으면 `진행중인 작업 없음`
- SQLite 작업 영속화, 컨테이너 재시작 시 미완료 작업 자동 재처리
- 최초 admin/admin 로그인 후 필수 비밀번호 변경, 관리자 비밀번호 해시 저장
- TOTP 2단계 인증: QR 코드·설정 키, 1회용 복구 코드 5개, 재인증 후 TOTP 삭제
- 서버 프로필/봇/TOTP 비밀정보 암호화 저장

## NAS에서 시작하기

Docker Engine과 Docker Compose v2가 필요합니다. Synology Container Manager 프로젝트에서도 동일한 Compose 파일을 사용할 수 있습니다.

```bash
git clone https://github.com/MaratangNearl/nasrelay.git
cd nasrelay
cp .env.example .env
```

`.env`에서 NAS 경로와 실행 계정 등을 수정합니다. 관리 비밀번호는 첫 로그인 후 웹에서 설정합니다.

```dotenv
NAS_PATH=/volume1/data
APP_DATA_PATH=./data
PUID=1000
PGID=1000
WEB_PORT=8080
```

- `NAS_PATH`: 전송에 사용할 NAS 호스트 폴더. 컨테이너의 `/nas`에 연결되며, 웹에서는 `/`로 표시됩니다. 필요한 공유 폴더만 지정하세요.
- `APP_DATA_PATH`: 대기열·이력·설정·암호화 키 저장 경로. `/data`에 마운트됩니다.
- `PUID`, `PGID`: NAS에서 `id`로 확인한 사용자/그룹 번호. 두 마운트 경로 모두 해당 사용자의 읽기·쓰기 권한이 필요합니다.
- `WEB_BIND`: 기본 `0.0.0.0`. NAS의 특정 LAN IP에만 바인딩하려면 수정합니다.

필요한 디렉터리를 미리 만들고 권한을 설정한 뒤 시작합니다. 아래 UID/GID는 `.env`와 일치하게 변경하세요.

```bash
mkdir -p data
sudo chown 1000:1000 data
# NAS_PATH 공유 폴더의 권한은 NAS 관리 화면에서 해당 계정에 부여합니다.
docker compose pull
docker compose up -d
```

브라우저 또는 스마트폰에서 `http://NAS_IP:8080`에 접속해 **아이디 `admin`, 비밀번호 `admin`**으로 로그인합니다. **12자 이상의 새 비밀번호로 변경하기 전에는 탐색·전송·설정 API를 사용할 수 없습니다.** 이후에는 변경한 비밀번호로 로그인합니다.

이미지 게시 전이나 소스에서 직접 빌드하려면:

```bash
docker compose -f compose.yaml -f compose.build.yaml up -d --build
```

## 웹 UI 사용법

1. **프로필 추가**에서 이름, 프로토콜, 주소, 포트, 계정, 비밀번호, 기본 폴더를 입력합니다. 주소에는 프로토콜 없이 호스트/IP만 입력합니다.
2. **저장 및 연결**을 누릅니다. 연결과 폴더 목록 조회가 모두 성공해야 연결됨으로 표시됩니다. **저장만 하기**로 연결 없이 프로필을 보관할 수도 있습니다.
3. 상단 **서버 프로필**에서 작업할 서버를 선택합니다. **선택 서버 연결**로 연결한 후 원격 서버와 내 NAS에서 원본 및 대상 폴더를 엽니다. 다른 서버를 선택해도 이미 연결한 서버는 연결 상태를 유지합니다.
4. 데스크톱은 행을 클릭하거나 빈 영역에서 드래그해 선택합니다. Ctrl/⌘로 선택을 추가/해제하고 Shift로 범위를 선택합니다. 모바일은 체크박스로 선택합니다. 폴더 이름을 누르면 해당 폴더가 열립니다.
5. **복사** 또는 **이동**을 고르고 **NAS로** / **서버로**를 누른 뒤 대상 경로를 확인해 시작합니다.
6. 이제 브라우저를 닫아도 됩니다. 다시 접속하면 진행 중인 작업과 기록을 확인할 수 있습니다.

**프로필 관리**에서 저장된 서버를 수정·선택·연결·해제·삭제합니다. 비밀번호를 비우면 같은 프로토콜·주소·포트·계정일 때만 기존 비밀번호를 유지합니다. 연결 정보를 수정하면 해당 프로필을 다시 연결해야 합니다. 프로필 수정·삭제·연결 해제는 이미 등록한 작업에 영향을 주지 않으며, 전송 확인 시 선택한 서버와 경로가 작업에 고정됩니다. 프로필과 선택 상태는 재시작 후에도 유지되고, 탐색용 연결은 다시 확인해야 합니다.

프로토콜별 설정:

| 프로토콜 | 기본 포트 | 설정 |
| --- | --- | --- |
| FTP / FTPS | 21 | FTPS는 명시적 TLS 옵션 사용. 패시브 모드와 파일 이름 인코딩 선택 가능 |
| SFTP | 22 | 계정 비밀번호와 서버의 `SHA256:…` 호스트 키 지문 입력 |
| WebDAV HTTPS | 443 | HTTPS 기본 사용, 인증서 검증 활성화, Basic 인증 |
| WebDAV HTTP | 80 | HTTPS 옵션을 해제하면 HTTP 사용 |

WebDAV 기본 폴더에는 `/remote.php/dav/files/사용자`처럼 서버의 DAV 서비스 경로를 입력합니다. 호스트 칸에는 서비스 경로를 넣지 않습니다. 서버에서 PROPFIND·GET·PUT·MKCOL·MOVE·DELETE를 허용해야 합니다. SFTP 지문은 서버 관리자에게 확인하거나 서버에서 `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub -E sha256` 등으로 확인합니다. 지문을 비우면 실행 환경 계정의 `~/.ssh/known_hosts`에 등록된 키만 허용합니다. 개인 키 인증은 현재 지원하지 않습니다.

선택한 폴더는 폴더 이름을 포함해 대상 경로 아래에 생성됩니다. 폴더 내부 파일과 폴더를 중복 선택하면 한 번만 처리합니다. 같은 대상 이름이 있으면 덮어쓰지 않고 해당 파일을 실패로 표시하며 나머지 파일을 계속 처리합니다. 원인을 해결한 뒤 **재시도**하면 완료된 파일은 다시 전송하지 않습니다.

**연결 해제**는 새 탐색과 작업 등록을 중지합니다. 이미 등록된 작업은 등록 당시의 서버 설정으로 계속됩니다. 전송 제어는 대기열의 **일시정지 / 재개 / 작업 취소**를 사용합니다. 서버 응답이 없는 경우 정지·취소 반영은 네트워크 제한 시간(통상 30초)까지 걸릴 수 있습니다. 일시정지 시 완료 파일은 보존하고 현재 미완료 파일의 임시 데이터를 정리합니다. 재개하면 그 파일을 처음부터 다시 전송하며, 바이트 단위 이어받기는 지원하지 않습니다. 일시정지 상태는 컨테이너를 재시작해도 유지됩니다.

각 탐색기의 **표시 필터**에서 수정 날짜와 만든 날짜를 따로 켜고 끌 수 있습니다. **정렬**에서 제목·수정 날짜·만든 날짜·크기를 선택하고 방향 버튼으로 오름차순/내림차순을 바꿉니다. 폴더는 항상 먼저 표시하며, 제공되지 않는 날짜는 `—`로 표시하고 같은 종류의 항목 중 마지막에 배치합니다. 날짜는 브라우저의 현지 시간대로 표시합니다. NAS의 만든 날짜는 파일 시스템의 실제 생성 시각을 사용하며, 지원하지 않는 파일 시스템에서는 표시되지 않습니다. FTP는 서버의 `create` 속성, WebDAV는 `creationdate` 속성을 사용합니다. 현재 SFTP 연결에서는 만든 날짜를 제공하지 않습니다.

## 계정 보안 · TOTP

왼쪽 메뉴의 **계정 보안**에서 비밀번호와 TOTP를 관리합니다. 계정 이름은 `admin`입니다.

1. **인증 앱 (TOTP)**에서 현재 비밀번호를 입력하고 **QR 코드 및 설정 키 생성**을 누릅니다.
2. Google Authenticator 등 호환 인증 앱으로 QR 코드를 스캔하거나 설정 키를 직접 입력합니다. QR은 서버에서 생성하며 외부 QR 서비스로 키를 전송하지 않습니다.
3. 인증 앱의 6자리 코드를 입력해 활성화합니다. 등록 요청은 10분 후 만료되며, 확인 전에는 TOTP가 켜지지 않습니다.
4. 표시되는 **복구 코드 5개**를 다운로드하거나 안전한 곳에 별도로 저장합니다. 이 화면을 닫으면 원문을 다시 조회할 수 없습니다. 각 코드는 한 번만 사용 가능합니다.
5. 다음 로그인부터 비밀번호 확인 후 TOTP 또는 복구 코드를 입력합니다. 복구 코드로 로그인해도 TOTP가 자동 삭제되지는 않습니다.

**TOTP 삭제:** 계정 보안에서 현재 비밀번호와 **사용하지 않은** TOTP 또는 복구 코드를 입력합니다. 삭제 즉시 설정 키와 남은 복구 코드가 폐기됩니다. 새 복구 코드가 필요하면 TOTP를 삭제한 뒤 다시 등록하세요.

같은 TOTP는 재사용할 수 없습니다. 로그인 직후 보안 설정을 변경할 때는 인증 앱에서 다음 코드가 나올 때까지 기다리거나 다른 복구 코드를 사용하세요. NAS와 스마트폰의 시간을 동기화해야 합니다. 코드에는 전후 30초의 시계 오차를 허용합니다.

비밀번호는 scrypt 해시, 복구 코드는 해시로 저장하며 TOTP 키는 `/data/secret.key`로 암호화합니다. 비밀번호 변경과 TOTP 활성화·삭제는 다른 로그인 세션을 종료합니다. 비밀번호는 재시작해도 유지되며 환경 변수로 덮어쓸 수 없습니다.

## 텔레그램 설정

1. 텔레그램 **@BotFather**에게 `/newbot`을 보내 전용 봇을 생성합니다.
2. 만든 봇의 **개인 대화**에서 `/start`를 보냅니다.
3. 웹 UI의 **텔레그램 설정**에 봇 토큰과 본인의 양수 Chat ID를 입력합니다.
4. **테스트 알림 보내기**로 수신을 확인하고 **설정 저장**을 누릅니다.

Chat ID는 봇에 메시지를 보낸 후 `getUpdates`의 `message.chat.id`에서 확인할 수 있습니다. 앱에서 봇을 활성화하기 전에 로컬 터미널에서 조회하세요. 다음 예제는 토큰을 터미널에 표시하지 않고 셸 히스토리·프로세스 인자에 토큰을 남기지 않습니다. `jq`가 필요합니다.

```bash
read -rsp 'Bot token: ' RELAY_BOT_TOKEN
printf '\n'
printf 'url = "https://api.telegram.org/bot%s/getUpdates"\n' "$RELAY_BOT_TOKEN" \
  | curl --config - --silent --show-error \
  | jq '.result[] | .message.chat | {id, type}'
unset RELAY_BOT_TOKEN
```

앱은 웹훅 대신 long polling을 사용하므로 텔레그램용 포트 포워딩이 필요하지 않습니다. 봇은 **하나의 앱 인스턴스에서만** 사용하세요. 기존 웹훅이 있는 봇은 Bot API의 `deleteWebhook`으로 먼저 해제해야 합니다. 등록된 **개인 대화의 Chat ID만** 명령에 응답하며, 그룹 대화는 지원하지 않습니다.

`/status` 예시:

```text
🔄 전송 중 · 9fd5c21b
FTP → NAS · 42.5%
17/40개 · 4.2 GiB/10.0 GiB
현재 속도: 12.5 MiB/s
/미디어/영상.mp4
```

현재 속도는 조회 시점의 최근 5초간 실제 전송 바이트로 계산합니다. 웹은 약 1초마다 갱신하고, 텔레그램 `/status`는 명령을 처리하는 시점에 같은 측정값을 조회합니다. 데이터가 들어오지 않으면 속도가 줄어 0이 되며, 대기·일시정지·완료 상태에서는 0으로 표시합니다. 재시도 중 다시 받은 바이트도 실제 전송속도에는 포함되지만 완료 용량에는 중복 합산하지 않습니다.

전송 제어 명령:

| 명령 | 동작 |
| --- | --- |
| `/pause [작업ID]` | 전송 중 또는 대기 중인 작업 일시정지 |
| `/resume [작업ID]` | 일시정지한 작업 재개 |
| `/cancel [작업ID]` | 전송 중·대기 중·일시정지한 작업 취소 |
| `/status` | 진행률, 현재 전송속도, 작업 ID, 일시정지 상태 조회 |

`/status`에 표시되는 ID의 앞 8자 이상을 입력할 수 있습니다. ID를 생략하면 실행 중인 작업을 우선 선택합니다. 대상이 여러 개여서 모호하면 작업 ID를 요청하며 임의로 여러 작업을 변경하지 않습니다. 일시정지 중에도 `/resume`, `/cancel`을 사용할 수 있습니다. `/help`로 명령 목록을 확인하세요. 설정한 개인 Chat ID에서만 제어할 수 있습니다.

성공·실패·취소 알림에는 완료한 파일 수/전체 파일 수와 완료한 용량/전체 용량을 보냅니다. 폴더 탐색 단계에서 실패하면 전체 파일 수·용량을 아직 계산하지 못해 0으로 표시될 수 있습니다. 알림 전송 실패는 파일 전송 결과에 영향을 주지 않으며 재시도합니다. 네트워크 장애 직후에는 같은 알림이 중복 도착할 수 있습니다.

## 데이터 보호와 재시작 동작

- 기본은 **복사**입니다. **이동**은 파일별 전송·크기 확인·최종 파일 반영 이후 원본을 삭제합니다. 원본 삭제 실패도 작업 실패로 알립니다. 이미 복사된 파일을 재시도하면 원본 정리부터 다시 시도합니다.
- 크기 검증은 암호학적 체크섬 검증이 아닙니다. 전송 대상 폴더를 다른 프로그램이 동시에 수정하지 않도록 하세요. FTP는 서버에 따라 rename의 원자성·덮어쓰기 동작이 다릅니다. 게시 직전에 충돌을 검사하지만 외부 프로그램과의 동시 쓰기를 완전히 잠글 수 없습니다.
- 전송 도중 원본 크기나 수정 시간이 바뀌면 원본을 보존하고 실패로 처리합니다. FTP 서버가 수정 시간을 제공하지 않으면 크기로 확인합니다.
- 전송 중에는 `.ftn-<작업ID>-<파일번호>.part` 임시 파일을 사용합니다. `.ftn-` 이름은 앱 전용으로 예약되며 탐색기에서 숨겨집니다.
- NAS 다운로드의 임시 파일은 전송 중 `0600`으로 보호하고, 검증을 마친 파일은 같은 폴더의 일반 파일 생성 권한(프로세스 umask와 폴더 기본 ACL 적용)으로 반영합니다. 예를 들어 일반 파일이 `0644`로 생성되는 환경에서는 완료 파일도 `0644`가 됩니다. 파일마다 `0777`을 강제하거나 서버 전체의 umask를 변경하지 않습니다.
- 미완료 작업과 파일별 완료 단계는 SQLite에 저장합니다. 재시작하면 완료 파일은 유지하고, 미완료 파일은 **처음부터 다시 전송**합니다. 바이트 단위 이어받기는 지원하지 않습니다.
- WebDAV의 개별 파일 속성 조회가 404이면 부모 폴더의 최신 목록으로 다시 확인합니다. 폴더 경로의 끝 슬래시 유무도 확인하며, 대기열 실행 시점에 폴더와 다운로드 주소를 조회합니다. 다운로드 연결 끊김, 404·410 또는 리디렉션 후 403은 파일당 최대 3회까지 새 연결과 주소로 시도합니다. 불완전 임시 파일을 정리하고 해당 파일을 처음부터 다시 받으며, 이동의 원본 삭제는 검증을 끝낸 뒤 진행합니다.
- 취소 시 이미 끝난 파일은 유지합니다. 이동 작업에서 이미 완료된 파일의 원본 삭제는 되돌리지 않습니다. 진행 중 파일의 불완전 임시 파일은 정리합니다. 최종 반영 대기 중인 완전한 임시 파일은 재시도를 위해 남을 수 있습니다.
- 이동 후 비어 있는 원본 하위 폴더를 정리합니다. 새 파일이나 권한 문제로 비어 있지 않은 폴더는 남기고 경고를 표시합니다.
- `/data`의 `app.sqlite3`와 `secret.key`를 **함께** 보관해야 복구할 수 있습니다. 암호화 키를 분실하면 저장된 서버/봇 자격증명을 복구할 수 없습니다. 일관된 백업은 컨테이너를 중지한 상태에서 `/data` 전체를 복사하세요.
- 심볼릭 링크와 특수 파일은 지원 대상에서 제외합니다. FTP 기본 폴더는 탐색 시작점입니다. 서버 자체의 사용자별 폴더 접근 제한(chroot/ACL)도 적용하세요.
- 웹 UI는 최근 100개 작업을 보여주며 상단 집계도 이 범위를 기준으로 합니다. 서로 다른 서버의 작업은 최대 4개까지 동시에 처리합니다. 같은 서버 설정의 작업과 서로 겹치는 NAS 원본·대상 경로를 사용하는 작업은 순서대로 처리합니다. 중첩 깊이 64단계, 작업당 탐색 항목 100,000개, 등록 원본 1,000개, 대기열 100개 제한이 있습니다.
- 웹 로그인은 24시간 후 만료되고 컨테이너를 재시작해도 다시 로그인해야 합니다. 전송에는 영향이 없습니다.

LAN에서 사용하거나 VPN/HTTPS 리버스 프록시로 접속하세요. HTTPS 프록시 뒤에서는 `.env`에 `COOKIE_SECURE=true`를 설정합니다. 일반 FTP는 계정과 파일을 암호화하지 않으므로 서버가 지원하면 **명시적 TLS (FTPS)**를 켜세요. FTPS 인증서 검증은 활성화되어 있습니다.

## 업데이트

```bash
docker compose pull
docker compose up -d
```

`latest`는 안정 버전 태그에서 발행됩니다. 버전을 고정하려면 `compose.yaml`의 이미지 태그를 `1.2.2`으로 바꿉니다. `main` 개발 빌드는 `edge` 태그로 게시됩니다.

### 이전 다운로드 파일이 SFTPGo에서 열리지 않는 경우

v1.2.0 이하에서는 WebDAV·FTP·SFTP에서 NAS로 받은 파일이 전송 완료 후에도 `0600`으로 남을 수 있었습니다. NAS 폴더를 공유하는 SFTPGo가 다른 OS 사용자로 실행되면 기존 파일은 열리지만 이 복사본만 읽지 못할 수 있습니다. SFTPGo의 사용자 권한 `*`와 별도로 [실제 파일 시스템 권한도 적용됩니다](https://docs.sftpgo.com/Enterprise/localfs/#permissions).

업데이트는 이미 받은 파일의 권한을 자동으로 바꾸지 않습니다. 다시 다운로드하지 않고 특정 파일만 복구하려면, 아래 경로를 nasrelay 탐색기에 보이는 실제 **파일 경로**로 바꿔 실행하세요. `/nas` 마운트 접두사는 붙이지 않습니다.

```bash
docker exec nasrelay python -m app.repair_permissions "/Movies/example.mp4"
```

명령은 지정한 `0600` 일반 파일만 부모 폴더의 일반 생성 권한으로 복구하고 파일 내용은 변경하지 않습니다. 다른 권한의 파일, 지정하지 않은 파일, 폴더와 진행 중 임시 파일은 바꾸지 않습니다. 복구 결과가 계속 `0600`이라면 컨테이너의 umask와 NAS 공유 폴더 기본 ACL에서 SFTPGo 실행 계정의 읽기 권한을 확인하세요.

관리 명령:

```bash
docker compose logs -f --tail=100
docker compose ps
docker compose stop
```

## 개발 및 테스트

Python 3.12 이상을 사용합니다. Node는 프런트엔드 구문 검사에만 필요하며 실제 앱은 번들러 없이 동작합니다.

```bash
python3 -m venv .venv
. .venv/bin/activate
pip install -r requirements.lock -r requirements-dev.txt
export DATA_DIR=./data
export NAS_ROOT=./nas
uvicorn app.main:app --host 127.0.0.1 --port 8080 --workers 1
```

```bash
python -m pytest -q
node --check app/static/app.js
docker compose --env-file .env.example config --quiet
```

테스트는 임시 NAS 디렉터리와 실제 로컬 FTP(`pyftpdlib`)·SFTP(`Paramiko`)·WebDAV HTTP 서버로 실행됩니다. 프로필 관리·연결 분리, 서버 간 동시 전송, 경로 충돌 보존, 프로토콜별 양방향 복사·이동을 검사합니다. 운영 NAS·서버·텔레그램 자격증명을 사용하지 않습니다. 운영 서버의 방화벽·패시브 포트·계정 권한과 실제 텔레그램 수신은 설치 후 확인해야 합니다.

브라우저 통합 확인(선택):

```bash
pip install playwright
playwright install --with-deps chromium
python scripts/browser_smoke.py
```

**애플리케이션 프로세스는 반드시 1개**로 실행하세요. SQLite 대기열은 하나의 애플리케이션 프로세스가 관리하며 Uvicorn `--workers 2` 이상 또는 동일 `/data`를 공유하는 복수 컨테이너는 지원하지 않습니다.

## GitHub Actions / GHCR 배포

워크플로는 테스트 후 `amd64`와 `arm64` 이미지를 빌드합니다. 저장소의 `GITHUB_TOKEN`과 `packages: write` 권한을 사용하며 별도 레지스트리 비밀번호를 저장하지 않습니다.

- `main` push: `ghcr.io/maratangnearl/nasrelay:edge`
- `v1.2.2` 태그 push: `:1.2.2`, `:1.2`, `:latest`
- Pull request: 테스트와 이미지 빌드만 실행, 레지스트리 push 없음
- 시험판 버전의 semver 태그는 `latest`로 승격하지 않음

다음 버전은 `app/__init__.py`, Dockerfile, 웹 UI, README와 워크플로의 컨테이너 검사 버전을 함께 수정하고 테스트한 뒤 태그를 생성합니다. 태그 빌드의 이미지 게시와 컨테이너 검사가 성공하면 변경 사항과 업데이트 방법을 담은 GitHub Release를 발행합니다.

```bash
git tag v1.2.3
git push origin main v1.2.3
```
